## 0. The one distinction to get right

Examiners ask this, and conflating the two is the commonest error:

| | Amazon Cognito | AWS IAM |
|---|---|---|
| Answers | *Who is this person?* | *What may this **AWS principal** do to **AWS resources**?* |
| Used here for | Application sign-in, JWTs | Lambda's access to DynamoDB, SQS, KMS, SES |
| Identities | Application users | Roles assumed by Lambda, and by browsers via the identity pool |
| Where enforced | Token verified in Lambda; roles checked by LifeLink's own RBAC | AWS evaluates every API call |

**LifeLink's user roles are not IAM.** `DONOR`, `BLOOD_BANK_ADMIN`,
`HOSPITAL_AUTHORIZER` and the other seven are application concepts in
`backend/src/appcore/rbac.py`, checked in process. No LifeLink user has an IAM
identity. There is exactly **one** `AWS::IAM::Role` written by hand in the
template (`MapReaderRole`); every other role is generated by SAM from the
`Policies:` on each function.

The system uses both, for their own jobs — §5 is the demonstration that shows
them side by side.

## 1. Authentication with Cognito

### The flow

OAuth 2.0 **Authorization Code with PKCE**, against the Cognito managed login
domain. The app client is **public and has no secret**, which is why PKCE is
required rather than optional.

```
Browser ──1── /login?client_id&response_type=code&code_challenge=S256(verifier)
          ←2── redirect to /auth/callback?code=...&state=...
       ──3── POST /oauth2/token  { code, code_verifier }     (no client secret)
          ←4── { access_token, id_token, refresh_token }
       ──5── GET /me   Authorization: Bearer <access_token>
```

### Source files

| Step | File |
|---|---|
| Build the authorize URL, generate and store the PKCE verifier | `frontend/src/auth/cognito.js` |
| Handle the redirect, exchange the code | `frontend/src/features/account/AuthCallbackPage.jsx` |
| Hold session state, attach the token to requests | `frontend/src/auth/AuthContext.jsx` |
| Sign-up / confirm / forgot-password (unauthenticated Cognito APIs) | `frontend/src/auth/cognitoSignUp.js` |
| Verify the token server-side | `backend/src/appcore/auth.py` → `CognitoTokenVerifier` |

### Things worth saying out loud

- **`state` is validated** on return, and the post-sign-in redirect is
  sanitised against open redirect — `frontend/src/auth/redirect.js`, 44 tests.
  `//evil.com` as a `pathname` was a real defect here.
- **Tokens live in `sessionStorage`, not `localStorage`** — scoped to the tab,
  so a token does not outlive the session on a shared machine.
- **Sign-out clears the session and redirects to the Cognito logout endpoint**,
  so the managed-login cookie goes too. Clearing only local state leaves the
  user silently signed in at the IdP.

### Console walkthrough

`Cognito ▸ User pools ▸ lifelink-dev`

| Look at | Expect |
|---|---|
| **App integration ▸ App clients** | One client, **no** client secret; Allowed flow: *Authorization code grant*; scopes `openid email profile` |
| **Sign-in experience** | Managed login enabled; domain prefix as deployed |
| **Users** | The demonstration accounts |
| **App integration ▸ Domain** | The `*.auth.ap-southeast-2.amazoncognito.com` login domain |

## 3. An unauthorized request being rejected

Four distinct refusals, each failing for a *different* reason. Showing all
four is far more convincing than showing one, because together they prove the
checks are independent.

**[run me]**

```bash
API=https://uk6itz2a5b.execute-api.ap-southeast-2.amazonaws.com/dev

# 1. No token at all on a protected route -> 401
curl -s -o /dev/null -w '%{http_code}\n' $API/me

# 2. A syntactically valid but forged token -> 401 (signature check fails)
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer not.a.token' $API/me

# 3. A forged token on a PUBLIC route -> 200, and the data is still public
#    Degraded auth must not break anonymous browsing.
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer not.a.token' \
  "$API/facilities?lat=30.3398&lon=76.3869&radiusKm=25"

# 4. A real DONOR token on an administrator route -> 403, not 401.
#    Authenticated but not permitted: a different answer from "who are you?".
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $DONOR_TOKEN" \
  $API/admin/audit
```

| # | Expected | Why it fails |
|---|---|---|
| 1 | `401` | no credential presented |
| 2 | `401` | JWKS signature verification fails |
| 3 | `200` | route is anonymous; a bad token is ignored, not fatal |
| 4 | `403` | identity fine, `audit:read` not held by `DONOR` |

The 401-versus-403 distinction is the part to draw attention to. Returning 401
for an authorization failure would tell a user to sign in again for a problem
signing in again cannot fix.

### Where this is enforced

`backend/src/appcore/auth.py` and `backend/src/appcore/rbac.py`. The
`@requires(...)` decorator runs **five ordered checks**:

1. authentication (unless the route is anonymous),
2. account status (a suspended account is refused),
3. permission held by one of the principal's roles,
4. organization scope — the resource belongs to the caller's organization,
5. ownership, for own-scope permissions such as `reservation:manage:own`.

Coverage: **33 authorization tests** in `backend/tests/unit/test_authorization.py`.

> **There is no API Gateway JWT authorizer**, and that is deliberate — do not
> let an examiner's assumption go uncorrected. The HTTP API is a single `ANY
> /{proxy+}` route and the Lambda verifies the token itself. The reason: the
> same API serves anonymous and authenticated routes, and per-route
> permissions plus organization scoping need application state (the user's
> roles and organization) that a gateway authorizer does not have. The
> trade-off is that an invalid token reaches Lambda and costs an invocation.

## 4. A Lambda execution role and its permissions

`infrastructure/template.yaml` — six functions (`ApiFunction`,
`NotificationWorker`, `WorkQueueWorker`, `OutboxPublisher`,
`PriorityDispatcher`, `ScheduledMaintenance`), each with its **own** generated
role, each granted only what it uses.

### The three findings worth presenting

**(a) The audit table is write-only, enforced by IAM.**

```yaml
# ApiFunction, template.yaml
- Statement:
    - Effect: Allow
      Action: ['dynamodb:PutItem', 'dynamodb:Query']   # no Update, no Delete
      Resource:
        - !GetAtt AuditTable.Arn
        - !Sub '${AuditTable.Arn}/index/*'
```

No `UpdateItem`, no `DeleteItem`. The application **physically cannot rewrite
its own audit history** — an application-level rule could be bypassed by a bug;
this cannot be bypassed by any code change short of redeploying the policy.
This is the strongest least-privilege point in the project.

**(b) KMS is scoped by condition, not by ARN.**

```yaml
- Effect: Allow
  Action: ['kms:GenerateDataKey', 'kms:Decrypt']
  Resource: '*'
  Condition:
    StringEquals:
      kms:ViaService: !Sub 'dynamodb.${AWS::Region}.amazonaws.com'
```

The tables use the AWS-managed DynamoDB key, whose id is not known at deploy
time, so `Resource` cannot name it. `Resource: '*'` with no condition would let
the function decrypt anything in the account. The `kms:ViaService` condition
narrows it to requests **DynamoDB makes on the function's behalf** — the
function cannot call KMS directly. Expect to be asked why `*` is acceptable
here; this is the answer.

**(c) Read versus write is per table, per function.**

| Function | Example grant |
|---|---|
| `NotificationWorker` (`lifelink-dev-notification-worker`) | `DynamoDBReadPolicy` on Organizations — reads recipients, cannot modify them |
| `WorkQueueWorker` (`lifelink-dev-work-worker`) | `DynamoDBReadPolicy` on Inventory, Facilities and Organizations; CRUD only on Alerts and Reservations |
| `ScheduledMaintenance` (`lifelink-dev-maintenance`) | `dynamodb:PutItem` **only** on Audit |
| `OutboxPublisher` (`lifelink-dev-outbox-publisher`) | CRUD on Outbox, `SendMessage` on two queues and its own DLQ, nothing else |

A single shared role with CRUD everywhere would have been less code. The split
is why a bug in the notification worker cannot corrupt an organization record.

### Console walkthrough

1. `Lambda ▸ Functions ▸ lifelink-dev-api` ▸ **Configuration ▸ Permissions**
2. Click the execution role to open it in IAM
3. Expand the inline policies — the statements above appear, resource-scoped
4. **Resource summary** shows exactly which tables and queues are reachable

That comparison *is* the least-privilege demonstration.

```yaml

  Resource: '*'
```

## 5. Cognito **and** IAM together — the identity pool

The best single demonstration of the distinction in §0, because both appear in
one request path.

The browser renders map tiles. Tiles come from Amazon Location, which is an
**AWS service**, so the browser needs **AWS credentials** — and a Cognito JWT
is not AWS credentials. The identity pool bridges the two:

```
Cognito user pool JWT  ──▶  Cognito identity pool  ──▶  sts:AssumeRoleWithWebIdentity
                                                   ──▶  temporary AWS credentials
                                                   ──▶  geo:GetMapTile
```

`MapReaderRole`, the only hand-written IAM role in the template:

```yaml
AssumeRolePolicyDocument:
  Statement:
    - Effect: Allow
      Principal: { Federated: cognito-identity.amazonaws.com }
      Action: 'sts:AssumeRoleWithWebIdentity'
      Condition:
        StringEquals:
          'cognito-identity.amazonaws.com:aud': !Ref IdentityPool   # this pool only
Policies:
  - PolicyName: ReadMapTilesOnly
    Statement:
      - Action: ['geo:GetMapTile', 'geo:GetMapStyleDescriptor',
                 'geo:GetMapSprites', 'geo:GetMapGlyphs']           # tiles only
```

Two controls to point at:

- The **trust policy condition** means a web identity from any *other* pool
  cannot assume this role. Without it, the role would be far more widely
  assumable than intended.
- The **permission policy** grants tile reads only — no `geo:SearchPlaceIndexForText`,
  no `geo:CalculateRoute`, no writes. Place search and routing are done by the
  backend, so no provider credential ever reaches the browser.

> **Be accurate about what is live.** The identity pool, the role and
> `lifelink-dev-map` were all deployed. The **shipped frontend does not use
> this path** — it renders OpenStreetMap raster tiles instead, because
> `AWS::Location::APIKey` is denied by the account's service control policy
> (see `docs/KNOWN_LIMITATIONS.md`). So demonstrate §5 **in the console, from
> the template**, and say that the browser currently takes the OSM route. Do
> not claim the map on screen is served through this role.

### Console walkthrough

1. `Cognito ▸ Identity pools ▸ lifelink_dev_identity` — note *unauthenticated
   identities enabled*, for anonymous visitors
2. **User access** — both authenticated and unauthenticated map to `MapReaderRole`
3. `IAM ▸ Roles ▸ MapReaderRole` ▸ **Trust relationships** — the `aud` condition
4. **Permissions** — the four `geo:` actions

## 6. DynamoDB access from the backend

**12 tables**, single-table-per-aggregate, all `PAY_PER_REQUEST`, `PK`/`SK`
composite keys, GSIs for every access pattern. Canonical definitions:
`backend/src/repositories/schema.py` — one source of truth consumed by the
local bootstrap, the integration tests and the template generator, so the
three cannot drift.

### What to show, in order

**(a) No scans.** Every read is a `Query` against a key or an index.
`Facilities` carries geohash indexes at precision 4, 5 and 6 so a radius
search reads a bounded set of cells. `GSI1-geo5`, `GSI2-geo6`, `GSI5-geo4`.

**(b) A conditional write preventing oversell.** The reservation pool counter
is updated inside a `TransactWriteItems` whose condition re-checks the
arithmetic. Two users requesting the last two units: both pass the advisory
domain check, **only one wins the transaction**.
`backend/src/repositories/reservation_repo.py` → `create_atomically`.

Say the ordering out loud, because it is the part that is easy to get
backwards: read inventory → read existing holds → *ask the domain* (advisory)
→ *attempt the atomic write* (decisive). Step 3 can say yes to two callers;
only step 4 decides.

**(c) Unknown is not zero, and (d) ranking is not a distance sort.** One query
shows both, and it is the single most convincing thing to run. Verified against
the live API on 24 November 2026.

**[run me]**

```bash
API=https://uk6itz2a5b.execute-api.ap-southeast-2.amazonaws.com/dev
curl -s "$API/facilities?lat=30.3398&lon=76.3869&radiusKm=100&bloodGroup=O-&component=PRBC" \
  | jq -r '.data.results[] | [.straightLineKm, .availability, (.eligibleUnits|tostring), .name] | @tsv'
```

> **Two details that matter.** The blood group is `O-`, **not** `O_NEG` — the
> API accepts the display form and answers `O_NEG` with a
> `VALIDATION_ERROR` listing the eight allowed values. And the radius must be
> **100 km**: at 25 km every facility in range has reported, so no `UNKNOWN`
> row appears and half the demonstration is missing.

Actual output, abridged:

| Rank | Distance | Availability | Units | Facility |
|---|---|---|---|---|
| 1 | 0.89 km | AVAILABLE | 9 | Urban Estate Donor Centre (DEMO) |
| 3 | 6.42 km | AVAILABLE | 12 | Patiala Community Blood Bank (DEMO) |
| **4** | **49.75 km** | AVAILABLE | 25 | Mohali Satellite Centre (DEMO) |
| 8 | 83.71 km | AVAILABLE | 3 | Ludhiana Metro Blood Bank (DEMO) |
| **9** | **24.77 km** | UNAVAILABLE | 0 | Rajpura Collection Centre (DEMO) |
| 12 | 56.06 km | **UNKNOWN** | **null** | Tricity Voluntary Blood Bank (DEMO) |

Point at two rows:

*   **Rank 4 versus rank 9.** A facility **49.75 km** away is ranked *above*
    one **24.77 km** away, because the nearer one holds zero units and the
    farther one holds 25. The list is not sorted by distance — it weighs
    availability, freshness, verification and distance together
    (`backend/src/domain/ranking.py`). If it were a distance sort the feature
    would be a map, not a recommendation.
*   **Rank 12.** `UNKNOWN` with `eligibleUnits: null` — **not** `0`. That
    facility has never reported; it is not a facility with no stock, and the
    two lead a user to opposite actions. It sorts last rather than being
    optimistically promoted. Guarded by 40 tests in
    `backend/tests/unit/test_unknown_is_not_zero.py`, which exists as its own
    file because this regressed once on one of two code paths.

> **Expect every facility to read `VERIFICATION_EXPIRED`.** This is correct
> behaviour, not a fault, and it is worth volunteering before you are asked.
> Verification carries an explicit expiry, the seeded verifications were
> recorded in November 2026, and the system refuses to keep calling a stale
> check current. It is the "updated is not verified" rule doing its job: the
> figures are fresh, the human verification behind them has lapsed, and the
> interface shows the two as separate badges. To demonstrate a live
> verification, re-verify a batch from the blood bank dashboard and watch the
> badge change.

## 7. Likely examiner questions

| Question | Short answer |
|---|---|
| Why DynamoDB and not RDS? | Access patterns are known and key-based; no joins. On-demand billing suits spiky, low-volume traffic, and there is no connection pool to exhaust from Lambda — which matters at a concurrency ceiling of 10. |
| Why is Lambda concurrency 10? | An account limit on this plan, not a design choice. It is the dominant architectural constraint: it pushed work to queues with DLQs, made idempotency mandatory, and ruled out fan-out designs. |
| How do you prevent double-booking? | Conditional `TransactWriteItems` on a pool counter. The domain check is advisory; the write is decisive. §6(b). |
| Is a user role an IAM role? | No. §0. |
| Why no API Gateway authorizer? | Mixed anonymous/authenticated routes and organization-scoped permissions need application state. §3. |
| How is the audit trail tamper-resistant? | IAM grants no `UpdateItem`/`DeleteItem` on that table. §4(a). |
| What happens if a queue consumer fails? | Every queue has a DLQ and every DLQ has a CloudWatch alarm. Messages are idempotent, so redelivery is safe. |
| Where are secrets? | Secrets Manager; none in the frontend bundle. The Cognito app client has no secret by design — it is a public client using PKCE. |
| What does it cost? | ~$0.40/month fixed. `docs/AWS_COST_ESTIMATE.md`. |
