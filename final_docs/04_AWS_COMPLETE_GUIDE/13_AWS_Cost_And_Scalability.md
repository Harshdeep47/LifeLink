# AWS Cost and Scalability

What LifeLink actually costs, why, and what would happen at real scale.

## 1. The headline — measured, not estimated

**Net payable: $0.00.**

Read from AWS Cost Explorer for **1–25 November 2026**:

| Line | Amount |
|---|---|
| **Gross usage** | **$0.1628** |
| **Credits applied** | **−$0.1628** |
| **Net payable** | **$0.00** |

**Keep those three distinct.** Gross usage is what the services actually
consumed. Credits are the FREE-plan allowance offsetting it. Net payable is
what the account is billed — zero.

### Projected full month

The window above is a **partial** month: the stack was created on
**15 November**, so the Secrets Manager secret had billed only about nine days
of its $0.40. A full month projects to roughly **$0.45–$0.50 gross**, still
**$0.00 net** while credits last.

| Account plan | FREE, status `ACTIVE` |
|---|---|
| Credits remaining | **$159.84** |
| Credits expire | **2027-05-15** |

At this burn rate the **credits expire long before they are exhausted** — about
$0.50 a month against $159.84 remaining. That is the honest framing: the
project is not free, it is *credited*.

**1. Two of those lines are audit cost, not application cost.**

| Service | Why it appears |

Explorer enumerating a service with **zero usage** — it is **not** evidence

| **S3** | 5 GB storage, 20,000 GET | a few MB, modest requests | far inside |
| **CloudFront** | 1 TB out + 10M requests/month | tiny | far inside |
| **API Gateway** | 1M HTTP API calls/month (12 months) | thousands | inside |
| **Cognito** | generous monthly active users | **11 users** | far inside |
| **SQS** | 1M requests/month | effectively zero | far inside |
| **SNS** | 1M publishes/month | 0 (no subscriptions) | free |
| **CloudWatch** | 5 GB logs ingested, 10 custom metrics, 10 alarms | ~12 MB logs, 8 alarms | inside |
| **KMS** | AWS-managed keys are **free** | 3 AWS-managed keys | free |

### The one thing that generates a charge, and why it is still there

The Secrets Manager secret **`lifelink/dev/provider-api-keys`** costs
**$0.40/month gross** — billed per month regardless of use — and accounted for
**70% of all gross usage** in the measured window.

**It has never been accessed.** Its **`LastAccessedDate` is `null`**: no
external provider is integrated in the demonstration environment, so nothing
has ever read it.

**Honest position:** deleting it would take gross usage to near zero, and the
seam in the code (`adapters/`) would remain. It was kept because the
external-ingestion route `POST /facilities/{id}/inventory/ingest` exists and is
meant to read a credential from it. **It has not been deleted and no AWS
resource was modified to produce these figures.**

Saying "forty cents gross for a capability we built and never connected — and
it's seventy percent of our bill" is a fine answer, and more interesting than
pretending the project is free.

## 3. The design decisions that made it cheap

These are the ones worth naming, because each is a deliberate trade:

| Decision | Saving | Trade-off |
|---|---|---|
| **DynamoDB on-demand** rather than provisioned | nothing idles | ~6–7x more per request at high steady volume |
| **HTTP API** rather than REST API | ~70% per call | no request validation, no WAF, no caching |
| **arm64** Lambda rather than x86 | ~20% per GB-second | the package must contain arm64 Linux wheels |
| **AWS-managed KMS key** rather than customer-managed | $1.00/month per key | cannot revoke the key or control rotation |
| **`PriceClass_100`** CloudFront | cheaper edges only | slightly higher latency outside those regions |
| **Six Lambdas sharing one package** | no duplication | each function carries code it does not use |
| **`KEYS_ONLY` / `INCLUDE` projections** on the two inventory GSIs | index storage and write cost | a missing attribute forces a second read |
| **No provisioned concurrency** | would bill continuously | cold starts remain |
| **PITR off on 4 ephemeral tables** | backup storage | those four are unrecoverable, which is fine as they self-delete |
| **No NAT Gateway, no VPC** | **~$32/month** | Lambdas run outside a VPC |

**That last row is the biggest saving in the list and the one students most
often miss.** Putting Lambda functions in a VPC to reach private resources
requires a NAT Gateway for outbound internet access, which costs roughly
$32/month *before* data processing charges — nearly a hundred times our whole
bill. Our functions need no VPC, because DynamoDB, SQS and Cognito are all
reached over their public API endpoints with IAM authentication.

**Say this:**
> "The single biggest cost we avoided is a NAT Gateway. If our Lambdas were in a
> VPC — which people often do by reflex — we'd need one for outbound internet
> access, and that's about thirty-two dollars a month before data charges, which
> is roughly eighty times our entire bill. We don't need a VPC, because
> DynamoDB, SQS and Cognito are all reached over their public endpoints with IAM
> authentication rather than network-level access control."

## 4. The one real cost risk

**CloudWatch Logs retention**, found during this documentation pass.

| Log group | Retention | Size |
|---|---|---|
| `/aws/apigateway/lifelink-dev` | 30 days | 162 KB |
| `/aws/lambda/lifelink-dev-api` | 30 days | 303 KB |
| `/aws/lambda/lifelink-dev-dispatcher` | **never expire** | **8.2 MB** |
| `/aws/lambda/lifelink-dev-maintenance` | **never expire** | 1.4 MB |
| `/aws/lambda/lifelink-dev-outbox-publisher` | **never expire** | 1.8 KB |
| `/aws/lambda/lifelink-dev-work-worker` | **never expire** | 957 B |

The template sets `LogRetentionDays: 30` and declares **two** log groups. The
other four were auto-created by Lambda on first invocation and inherited the
default of never expiring.

**The dispatcher runs every minute** — about 43,000 invocations a month — and
has accumulated 8.2 MB that will never be deleted. Negligible today, unbounded
over years. It is also the only part of this deployment whose cost grows
without a corresponding increase in usage.

Recorded as a limitation; **not fixed**, because of the engineering freeze.

## 5. Scalability — the honest answer

### What scales automatically

| Component | Behaviour |
|---|---|
| **CloudFront** | effectively unlimited; more traffic means more cache hits |
| **S3** | effectively unlimited |
| **DynamoDB on-demand** | scales to the previous peak instantly, then ramps |
| **API Gateway** | handles far more than we allow through |
| **Cognito** | millions of users |
| **SQS** | effectively unlimited |

### What does not

**Lambda concurrency is capped at 10.** That is the ceiling, and everything
else is sized to respect it:

| Mechanism | Value |
|---|---|
| API stage throttle | 10 req/s, burst 20 |
| SQS consumer concurrency | 2 each |
| Function timeout | 29 s |

### What "1000 concurrent users" would actually do

**Be precise rather than optimistic:**

> "As configured, it would not handle a thousand concurrent users, and I can
> tell you exactly where it breaks. CloudFront and S3 wouldn't notice — the
> static site would be fine, because it's cached at the edge. DynamoDB on-demand
> would cope. The bottleneck is Lambda: we have ten concurrent executions, so
> the gateway throttles at ten requests a second and everything beyond that gets
> a 429.
>
> The architecture doesn't need to change to fix it — the limits do. You'd raise
> the account concurrency limit, raise the stage throttle to match, and then
> probably split the API function by feature area so one slow route can't
> consume the whole pool. At that point the next thing to watch would be hot
> partitions in DynamoDB, since a single busy facility's inventory batches all
> share that facility's partition key."

### Cost at real scale — an order-of-magnitude sketch

For 100,000 requests/day (~3M/month), with a raised concurrency limit:

| Service | Rough monthly |
|---|---|
| Lambda (3M invocations, 512 MB, ~200 ms) | a few dollars |
| API Gateway HTTP API (3M calls) | ~$3 |
| DynamoDB on-demand (reads + writes + 24 GSIs) | **the largest line** — likely tens of dollars |
| CloudFront | a few dollars |
| CloudWatch Logs | grows with invocations; **retention matters here** |
| Secrets Manager | $0.40 (flat, regardless of scale) |

**At that point DynamoDB would be the thing to optimise**, and two levers
exist: switch high-volume tables to **provisioned capacity with auto-scaling**
(cheaper per request for predictable load), and revisit the 24 GSIs, since every
write propagates to every index on that table. `facilities` has five.

**That is a much better answer than "it scales because it's serverless."**

## 6. How to see the cost yourself

```bash
aws freetier get-account-plan-state --profile lifelink
```

Console paths:

| Where | What |
|---|---|
| AWS Settings -> Billing | invoices, spend limits, payment |
| AWS Billing and Cost Management console | Cost Explorer, budgets, free tier usage |
| **Billing -> Free tier** | per-service free tier consumption — the most useful page for this project |

**Note on this account:** billing, spend limits and invoices are managed in
**AWS Settings**, while budgets and cost optimisation live in the Billing and
Cost Management console. If resources suddenly return Access Denied on
operations that previously worked, a **spend limit** may have paused the
project — only a project owner can change it.

**For a demonstration**, the Free Tier usage page is the one to open: it shows
each service's consumption as a percentage, which makes "we're inside every
free tier except one secret" visible rather than asserted.

## 7. Cleaning up

If the project is finished with, resources can be removed:

```bash
# Deletes all 66 resources
aws cloudformation delete-stack --stack-name lifelink-dev --profile lifelink
```

**Before doing that, know what is lost:** all 12 tables and their 742 rows, the
Cognito pool and its 11 users, and the S3 buckets. Deletion protection is
**disabled** on every table, so nothing will block it.

**Worth asking the user first**, and worth noting that re-seeding can rebuild
the data but not the Cognito users without re-running
`scripts/provision_demo_logins.py`.

The cheaper middle ground, if the project needs to stay demonstrable: leave it
running. Gross usage is under fifty cents a month and FREE-plan credits
currently bring net payable to zero.

## 9. Follow-up questions

**"What's the most expensive thing if this went to production?"**
> DynamoDB, and specifically the indexes. Every write propagates to every GSI on
> that table, and the facilities table has five. At production write volume I'd
> audit whether all 24 are earning their keep, and move predictable high-volume
> tables to provisioned capacity with auto-scaling, which is substantially
> cheaper per request than on-demand for steady load.

**"Is serverless always cheaper?"**
> No, and that is worth saying. Lambda and on-demand DynamoDB are cheap when
> traffic is spiky or low, because you pay nothing at idle. But per request they
> are more expensive than a running server. There is a crossover: a steady
> high-volume workload is cheaper on EC2 or ECS with reserved capacity. For a
> demonstration project with bursty traffic, serverless wins by a wide margin.

**"Could you make it completely free?"**
> Yes — delete the Secrets Manager secret, and the fixed cost goes to zero. It
> exists for external provider credentials on the inventory ingestion route,
> which isn't connected to a real provider — its last-accessed date is null — so
> it's forty cents gross for a capability we built and never wired up. That's
> seventy percent of our gross bill. Net it's zero, because credits cover it.

**"What happens if you exceed the free tier?"**
> On this account plan there may be a spend limit that pauses the project if
> exceeded. The symptom is confusing — operations that worked suddenly return
> Access Denied. It's checked in AWS Settings under Billing, and only a project
> owner can change it.
